# MISHWAR - TASK 16 UI/UX Audit and Repair

تاريخ التنفيذ: 2026-10-10  
النطاق: تطبيق العميل، تطبيق الكابتن، ومكوّنات Flutter المشتركة.  
القيود الملتزم بها: لم يتم تعديل Backend أو Firebase أو Authentication أو عقود API. لم يتم تنفيذ commit أو push.

## ملخص القرار

تم تنفيذ إصلاحات UI/UX مركزة دون إعادة تصميم كامل. حافظت التعديلات على FAST وBIDDING، وأضافت حماية واجهة ضد أخطاء وتكرار عمليات مثبتة، وحسّنت وضوح الهوية والحالات المالية والحجز.

الحالة بعد TASK 16: مناسبة أكثر للاختبار المحلي وPilot UI review، لكنها لا تثبت جاهزية Production لأن Firebase/Backend السحابي والأجهزة الحقيقية خارج نطاق هذه المهمة.

## المشاكل المثبتة قبل الإصلاح

1. الهوية البصرية كانت غير موحدة بالكامل: الثيم لا يحدد NavigationBar/Button/Chip بشكل مركزي، والكروت كانت بزوايا كبيرة وغير مناسبة لواجهة تشغيلية كثيفة.
2. اتجاه RTL كان يعتمد غالباً على MaterialApp locale، لكن بعض اختبارات الشاشات المباشرة لا تفرض RTL.
3. اختيار المركبة في تطبيق العميل كان Dropdown نصي، أقل وضوحاً من المتوقع في تطبيق نقل.
4. وضع BIDDING في تطبيق العميل كان يسمح بمحاولة طلب عروض بسعر مقترح فارغ أو غير صالح من الواجهة.
5. تطبيق الكابتن كان يسمح بمحاولة إرسال عرض ثانٍ لنفس طلب BIDDING من الواجهة قبل سحب العرض السابق.
6. شاشة "حسابي المالي" في تطبيق الكابتن كانت تعرض شرائح مالية مكررة.
7. عند عدم تحميل بيانات المالية، كانت الواجهة تميل لعرض أصفار، وهذا قد يلتبس مع أرصدة مالية حقيقية.

## الإصلاحات المنفذة

### الهوية البصرية

- توحيد ثيم الأزرار، NavigationBar، Chips، حقول الإدخال، والكروت في `MishwarBrand`.
- تقليل زوايا الكروت والحقول إلى 8px لتصبح الواجهة أكثر تشغيلية وأقل زخرفة.
- تحسين تباين الأزرار وحدود العناصر الثانوية.

### RTL والتنقل

- فرض `Directionality.rtl` داخل الشاشات الرئيسية للعميل والكابتن، حتى عند تشغيل الشاشة مباشرة داخل الاختبارات.
- الحفاظ على NavigationBar الحالي وعدم تغيير مسارات التنقل أو الـ API.

### تطبيق العميل

- استبدال اختيار نوع المركبة من Dropdown إلى شبكة اختيار واضحة بأيقونات:
  - سيارة اقتصادية.
  - دراجة نارية.
  - سيارة مريحة.
  - سيارة عائلية.
- عند اختيار الدراجة، يتم الحفاظ على السلوك الموجود: راكب واحد وتعطيل المكيف.
- إضافة تحقق واضح لسعر BIDDING: لا يتم إرسال طلب عروض إذا كان السعر فارغاً أو غير صالح.
- إضافة guard ضد تكرار `_requestRide` و`_selectBid` أثناء وجود عملية جارية.

### تطبيق الكابتن

- إضافة guard ضد تكرار إجراءات الرحلة أثناء `_busy`.
- منع إرسال عرض BIDDING مكرر لنفس الرحلة من الواجهة قبل سحب العرض السابق.
- تحسين شاشة "حسابي المالي":
  - إزالة الشرائح المالية المكررة.
  - عرض حالة واضحة عند عدم تحميل البيانات المالية.
  - عدم عرض أصفار كأرصدة حقيقية عند غياب استجابة المالية.

### الاختبارات

- إضافة اختبار Widget للعميل يغطي ظهور خيارات المركبة ومنع إرسال BIDDING بسعر غير صالح.
- إضافة اختبار Widget للكابتن يغطي منع إرسال عرض مكرر لنفس طلب BIDDING.
- تحديث بيانات Fake API المالية في اختبار الكابتن لتغطي الحقول المالية المعروضة.

## ما لم يتم تنفيذه

- لم يتم تعديل Backend أو Firebase أو Auth.
- لم يتم تشغيل التطبيق على جهاز Android فعلي.
- لم يتم التقاط صور قبل/بعد، لأن المهمة لم تتضمن تشغيل واجهة فعلية على متصفح/جهاز في هذه الجولة.
- لم يتم بناء APK/AAB.
- لم يتم اختبار FCM أو GPS الحقيقي لأن ذلك يتطلب Firebase/جهاز فعلي.

## المخاطر المتبقية

- يجب اختبار كل الواجهات على أجهزة Android صغيرة ومتوسطة وكبيرة.
- يحتاج BIDDING إلى اختبار يدوي كامل بين جهاز عميل وجهاز كابتن بعد ربط السحابة.
- يجب مراجعة أيقونات التطبيق وشاشة البداية النهائية قبل Google Play.
- يجب التحقق من أن تغييرات الثيم لا تؤثر على أي شاشة إدارية أو مستقبلية تستخدم الحزمة المشتركة.
